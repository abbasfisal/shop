افزودن دستور db:wipe — پاک‌سازی کامل اشیای دیتابیس (معادل php artisan db:wipe)

تاریخ: ۲۰۲۶-۰۲۷ / ۱۳:۲۹  •  مسیر گزارش: reports/2026-09-27_1329_db-wipe-command.html

۱. عنوان و خلاصهٔ اجرایی

دستور go run . db:wipe (و هدف make db-wipe) به پروژه اضافه شد: این دستور با پرسش از کاتالوگ‌های PostgreSQL، تمام اشیای قابل حذف (view/matview، جدول، sequence، function/procedure، domain/enum/range/composite type) را در همهٔ اسکیماهای غیرسیستمی پیدا کرده، به‌صورت یک تراکنش واحد با DROP ... CASCADE حذف می‌کند. خود دیتابیس، اسکیماها و extensionها (مثل pg_trgm) دست‌نخورده می‌مانند؛ رفتاری که دقیقاً با php artisan db:wipe برابر است. روی ترمینال، قبل از اجرا تأیید yes می‌گیرد و با --force می‌توان از آن رد شد. چرخهٔ کامل migrate → db:wipe → migrate روی یک دیتابیس موقت تست و تأیید شد.

۲. درخواست اصلی

add db:wipe comamnd to drop db like php artisan db:wipe

در ادامه، با یک پرسش کوتاه دامنهٔ رفتار روشن شد و کاربر گزینهٔ «Drop all schema objects (مثل artisan)» را انتخاب کرد؛ یعنی اشیای درون دیتابیس حذف شوند، نه خود دیتابیس.

۳. زمینه و کشف

  • graphify query "how do cobra commands connect to postgres and run migrations" — نشان داد فرمان‌های cobra در cmd/ همگی از openMigrateDB() (در cmd/migrate.go:25) استفاده می‌کنند که postgres.Connect() را صدا زده و هندل *sql.DB برمی‌گرداند. نتیجه: دستور جدید هم باید همین مسیر را طی کند.
  • فایل‌های خوانده‌شده: cmd/migrate.go، cmd/root.go، cmd/seed.go، infrastructure/database/postgres/postgres.go، bootstrap/bootstrap.go (برای فهم بارگذاری .env)، Makefile، README.md، doc/database.md.
  • بازرسی دیتابیس واقعی با psql: فقط اسکیمای public، فقط extensionهای plpgsql؛ مایگریشن‌ها CREATE EXTENSION، CREATE FUNCTION یا CREATE SCHEMA ندارند.
  • وابستگی‌ها: github.com/pressly/goose/v3 و github.com/spf13/cobra از قبل در go.mod هستند؛ golang.org/x/sys به‌صورت indirect موجود بود و به direct ارتقا یافت (بدون نیاز به شبکه).

۴. تصمیم‌ها و چرایی (ADR-style)

۴.۱ دامنهٔ wipe: اشیای اسکیما یا خود دیتابیس؟

گزینه‌های بررسی‌شده

  1. حذف همهٔ اشیای اسکیما (رفتار artisan db:wipe) — جدول‌ها/viewها/sequenceها/routineها/typeها حذف، دیتابیس می‌ماند.
  2. DROP DATABASE + CREATE DATABASE — نیازمند اتصال به دیتابیس نگهدارنده (postgres)، قطع همهٔ اتصال‌ها و دسترسی CREATEDB؛ ریسک اختلاف ENCODING/LC_COLLATE هنگام بازسازی.
  3. هر دو با فلگ --drop.

انتخاب: گزینهٔ ۱ (تأییدشده توسط کاربر).
چرا رد شد بقیه: گزینهٔ ۲ در محیط توسعهٔ این پروژه (کاربر shop، بدون دسترسی superuser لزومی) شکست می‌خورد و migrate بعد از آن هم به دسترسی CREATE دیتابیس نیاز داشت؛ ریسک پذیرفته‌شده: دستور خالی‌کردنِ خودِ دیتابیس را انجام نمی‌دهد.

۴.۲ مکانیزم حذف: SQL دستی از کاتالوگ یا DROP SCHEMA ... CASCADE؟

گزینه‌ها: (۱) تولید دستور DROP از pg_class/pg_proc/pg_type؛ (۲) DROP SCHEMA public CASCADE; CREATE SCHEMA public;؛ (۳) استفاده از goose Reset (یعنی همان migrate:reset).

انتخاب: گزینهٔ ۱.

چرا: گزینهٔ ۲ وقتی objectی متعلق به extension باشد خطای cannot drop ... because extension ... requires it می‌دهد و schemaهای سفارشی را هم نابود می‌کند؛ گزینهٔ ۳ فقط migrationها را برمی‌گرداند و دادهٔ دستی/جداول باقی‌مانده را پاک نمی‌کند (و Downهای شکسته عملاً کار نمی‌کنند). با تولید SQL از کاتالوگ، اشیای متعلق به extension با فیلتر pg_depend.deptype = 'e' مستثنا می‌شوند.

ریسک پذیرفته‌شده: اشیای خیلی عجیب (event trigger، publication، operator سفارشیِ وابسته به object حذف‌نشده) به‌صورت صریح فهرست نشده‌اند؛ اما CASCADE روی هر DROP وابستگی‌هایشان را هم می‌برد.

۴.۳ تراکنشی بودن اجرا

گزینه‌ها: اجرای هر DROP مستقل در یک اتصال یا اجرای همه در یک تراکنش.
انتخاب: یک تراکنش واحد (db.Begin() … Commit()). PostgreSQL از تراکنش DDL پشتیبانی می‌کند؛ اگر وسط کار خطا بیاید، هیچ‌چیزی حذف نشده و دیتابیس سالم می‌ماند.
ریسک پذیرفته‌شده: قفل شدن objectها تا پایان اجرای دستور (برای یک فرمان توسعه‌ای نامحسوس است).

۴.۴ تأیید کاربر و تشخیص ترمینال

گزینه‌ها: (۱) بدون تأیید؛ (۲) تأیید با تشخیص TTY؛ (۳) همیشه تأیید؛ (۴) فقط در production مثل Laravel.

انتخاب: گزینهٔ ۲ — روی ترمینال واقعی «yes» بپرس، در session غیرتعاملی با یک هشدار اجرا کن، فلگ --force برای رد شدن.

چرا: گزینهٔ ۳ در CI/لوله باعث EOF و شکست می‌شود (در اولین تست همین اتفاق افتاد)؛ گزینهٔ ۱ خطرناک است؛ پروژه مفهوم APP_ENV=production را ندارد پس شرط Laravel قابل پیاده‌سازی نبود.
تشخیص TTY: در لینوکس با unix.IoctlGetTermios(fd, unix.TCGETS) (در فایل با build tag)، در بقیهٔ پلتفرم‌ها با هوریستیک ModeCharDevice به‌جز /dev/null. دلیل رد راه‌حل سادهٔ ModeCharDevice: /dev/null هم character device است، پس < /dev/null اشتباهی prompt می‌زد.

۴.۵ ترتیب حذف

انتخاب: view → table → sequence → routine → type.
دلیل: اگر جدول‌ها اول حذف شوند، viewهای وابسته با CASCADE می‌روند و شمارش viewها صفر می‌شود؛ typeها آخر می‌آیند چون جدول/view ممکن است به ستونی از نوع enum/domain وابسته باشند. IF EXISTS روی همهٔ دستورها باعث می‌شود objectهایی که قبلاً با CASCADE رفته‌اند خطا ندهند.

۵. مراحل انجام کار

  1. کاوش ساختار فرمان‌های cobra با graphify query و خواندن cmd/migrate.go، cmd/seed.go، postgres.go.
  2. پرسش دامنهٔ رفتار از کاربر → «Drop all schema objects (مثل artisan)».
  3. بازرسی دیتابیس: psql -c "select extname from pg_extension" و لیست اسکیماها؛ بررسی مایگریشن‌ها با grep برای CREATE EXTENSION/TYPE/FUNCTION.
  4. نوشتن cmd/db.go (دستور، پنج کوئری کاتالوگ، تأیید، خلاصهٔ خروجی).
  5. نوشتن cmd/db_tty_linux.go و cmd/db_tty_other.go برای تشخیص ترمینال.
  6. go build ./... && go vet ./... و بعد go mod tidy (انتقال x/sys به direct).
  7. ساخت دیتابیس موقت wipe_scratch و اجرای POSTGRES_DB=wipe_scratch go run . migrate (۵۲ object).
  8. ساخت objectهای مصنوعی: اسکیمای analytics، enum mood، domain us_postal_code، sequence مستقل، function، view، جدول وابسته به type، extension pg_trgm.
  9. اجرای db:wipe در سه حالت (غیرتعاملی، ترمینال با «no»، ترمینال با «yes») و سپس migrate دوباره.
  10. به‌روزرسانی Makefile، README.md، doc/database.md، AGENTS.md.
  11. اجرای gofmt -l cmd/، go build، go vet، make test.
  12. حذف دیتابیس موقت: DROP DATABASE wipe_scratch.
go build ./... && go vet ./...          # BUILD_VET_OK
go mod tidy                             # فقط go.mod (یک خط: x/sys → direct)
gofmt -l cmd/                           # خروجی خالی
make test                               # بدون FAIL

# چرخه کامل روی دیتابیس موقت
psql "... dbname=postgres" -c "CREATE DATABASE wipe_scratch;"
POSTGRES_DB=wipe_scratch go run . migrate
POSTGRES_DB=wipe_scratch go run . db:wipe < /dev/null
POSTGRES_DB=wipe_scratch go run . migrate
psql "... dbname=wipe_scratch" -Atc "select count(*) ..."   # 52

۷. باگ‌ها و مشکلات برخوردشده

۷.۱ تشخیص ترمینال با ModeCharDevice اشتباه بود باگ

متن خطا: -- db:wipe read confirmation error: EOF / exit status 1

ریشه: /dev/null هم یک character device است، پس os.Stdin.Stat()&os.ModeCharDevice != 0 برای go run . db:wipe < /dev/null هم «terminal» گزارش می‌شد، prompt چاپ می‌شد و چون EOF بود خواندن fail می‌کرد.

-fix: تشخیص با unix.IoctlGetTermios(..., unix.TCGETS) (فقط terminal واقعی true می‌دهد) + فایل جایگزین برای غیرلینوکس که /dev/null را مستثنا می‌کند؛ ضمناً خطای خواندنِ prompt به‌جای log.Fatal حالا «aborted» با کد خروج ۱ چاپ می‌کند.

تأیید: با script -qec "go run . db:wipe" /dev/null (PTY مصنوعی) هم حالت «no» (abort و ۵۲ object باقی‌ماند) و هم حالت «yes» (۰ object) تست شد؛ حالت < /dev/null هم بدون prompt اجرا شد.

۷.۲ ابهام operator در کوئری‌های بازرسی test محیطی

متن خطا: ERROR: operator is not unique: text || "char"

ریشه: کوئری‌های SQL من برای راستی‌آزمایی، ستون‌های "char" مانند relkind/typtype را بدون ::text به string وصل می‌کردند. مربوط به کد محصول نبود؛ فقط اسکریپت بازرسی.

-fix: افزودن ::text. کوئری‌های داخل cmd/db.go از این مشکل مبرا هستند چون با quote_ident فقط identifier می‌سازند.

۷.۳ اشیای extension بعد از wipe باقی می‌مانند (رفتار درست، نه باگ) تأیید

بعد از wipe شمارش ۳۱ routine و ۲ type باقی ماند. بررسی نشان داد همگی متعلق به pg_trgm هستند (public.gtrgm و public._gtrgm و ده‌ها تابع gin_trgm_ops) و extension هم نصب است. این دقیقاً همان قاعدهٔ pg_depend.deptype='e' است: دیتابیس خالی می‌شود ولی infrastructure دست‌نخورده می‌ماند.

۹. نکات آموزشی

  • فرمان‌های cobra در این مخزن الگوی ثابتی دارند: init() → rootCmd.AddCommand(...)، و اتصال DB از طریق openMigrateDB() در cmd/migrate.go. فرمان جدید باید همین ورودی را استفاده کند تا تنظیمات .env یکسان اعمال شود.
  • godotenv.Load متغیرهای موجود در shell را override نمی‌کند؛ بنابراین POSTGRES_DB=wipe_scratch go run . db:wipe بدون هیچ تغییر کد، امکان تست روی دیتابیس موقت را می‌دهد — الگوی خوبی برای تست فرمان‌های مخرب.
  • حذف object در PostgreSQL تراکنشی است. برخلاف MySQL، می‌توان ده‌ها DROP را در یک تراکنش گذاشت و در صورت خطا همه را rollback کرد. این امن‌ترین راه برای یک فرمان ویرانگر است.
  • هرگز DROP SCHEMA ... CASCADE را به‌عنوان «wipe» استفاده نکنید: اشیای متعلق به یک extension (pg_depend.deptype='e') قابل حذف نیستند و دستور کل شکست می‌خورد؛ راه درست فیلتر کردن روی کاتالوگ است.
  • ترتیب DROP مهم است اگر می‌خواهید آمار درست بگیرید: view قبل از table تا با CASCADE حذف نشود، type بعد از table چون ستون‌ها به enum/domain وابسته‌اند.
  • تشخیص ترمینال با ModeCharDevice کافی نیست: /dev/null هم character device است؛ راه استاندارد در لینوکس ioctl(TCGETS) از golang.org/x/sys/unix است (با build tag تا cross-compile نشکند).
  • «خالی» یعنی خالی از اشیای شما، نه خالی مطلق: بعد از wipe همچنان extensionها و اسکیماها هستند؛ شمارش‌گیری برای پیام «nothing to drop» باید دقیقاً همان کوئری‌هایی را بگیرد که حذف می‌کنند.

۱۰. کارهای باقی‌مانده / ریسک‌ها

  • دستور روی go_shop_dev اجرا نشده (عمداً — دیتابیس توسعه حاوی داده است). برای استفاده: make db-wipe && make migration-up && make seed. اگر بخواهید، اجرایش را می‌توانم انجام دهم.
  • اشیای خارج از فهرست صریح (event trigger، publication، operator سفارشیِ standalone، foreign data wrapper) به‌صورت مستقل drop نمی‌شوند ولی معمولاً با CASCADE کنار objectهای اصلی می‌روند. در صورت نیاز می‌توان یک کوئری دیگر به wipeKinds اضافه کرد.
  • دادهٔ داخل objectهای موقتِ یک تراکنش large object (BLOB در pg_largeobject) حذف نمی‌شود — این پروژه از large object استفاده نمی‌کند (فایل‌ها روی دیسک هستند)، پس فعلاً نادیده گرفته شد.
  • اسکیماهای غیرpublic حذف نمی‌شوند فقط اشیای درون‌شان (رفتار Laravel)؛ اگر مایگریشنی DROP SCHEMA نداشته باشد، اسکیمای خالی باقی می‌ماند.
  • هیچ تست خودکار واحدی برای دستور اضافه نشد (نیاز به PostgreSQL واقعی دارد). اگر خواستید، می‌توان یک تست integration با شرط TEST_DATABASE_URL نوشت که طبق AGENTS.md در نبود آن skip می‌شود.
  • ریسک باقی‌مانده: db:wipe --force هیچ سؤالی نمی‌پرسد؛ در اسکریپت‌ها حتماً POSTGRES_DB را صریح ست کنید.

۱۱. نکات تکمیلی

نحوهٔ استفاده:

go run . db:wipe            # با تأیید روی ترمینال
go run . db:wipe --force    # بدون تأیید (CI/اسکریپت)
make db-wipe                # معادل make
POSTGRES_DB=other_db go run . db:wipe --force   # روی دیتابیس دیگر

# بعد از wipe حتماً اسکیما را بسازید:
go run . migrate            # یا: make migration-up && make seed

شکل خروجی موفق:

[postgres] connected to postgresql database successfully
[db:wipe] non-interactive session: wiping "wipe_scratch" without confirmation
[db:wipe] dropped 59 object(s) from "wipe_scratch" (view: 1, table: 28, sequence: 27, routine: 1, type: 2)
[db:wipe] run `go run . migrate` to rebuild the schema

تفاوت با migrate:reset: هر دو «شروع از صفر» می‌دهند، اما migrate:reset فقط migrationهای ثبت‌شده را با goose down برمی‌گرداند (اگر Down خراب/ناقص باشد می‌ماند)، در حالی که db:wipe وضعیت نهاییِ دیتابیس را صفر می‌کند و برای دیتابیس‌های آلوده به object دست‌ساز (data.sql، دستی، باقی‌مانده از نسخه قدیمی) راه مطمئن‌تری است.

نکتهٔ گراف دانش: پس از commit، هوک post-commit گراف را با فایل‌های cmd/*.go جدید بازسازی می‌کند؛ تغییرات README.md/doc/database.md/Makefile با /graphify --update لازم است اضافه شوند چون AST فقط کد Go را می‌خواند.

گزارش خودمختار — طبق AGENTS.md پس از اتمام هر تسک در پوشهٔ reports/ ساخته شده است.
